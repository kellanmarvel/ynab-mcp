# Release Process

This document outlines the standardized release process for YNAB MCP Server, including version management, automated workflows, and distribution procedures.

## 📋 Overview

The YNAB MCP Server uses an automated release process built on:
- **cargo-release** for version management and tagging
- **GitHub Actions** for building, testing, and publishing
- **Semantic versioning** for consistent version numbering

## 🚀 Quick Release

For maintainers with proper access, releasing is straightforward:

```bash
# Create new patch release (0.1.5 → 0.1.6)
cargo release patch

# Create new minor release (0.1.5 → 0.2.0)
cargo release minor

# Create new major release (0.1.5 → 1.0.0)
cargo release major

# Push the tag to trigger automated release
git push origin master --tags
```

The GitHub Actions workflow will automatically:
- Build binaries for all platforms
- Create GitHub release with changelog
- Publish to crates.io
- Update Docker images

## 📚 Detailed Process

### Prerequisites

1. **Permissions**: Write access to the repository
2. **Tools**: `cargo-release` installed (`cargo install cargo-release`)
3. **Clean State**: No uncommitted changes
4. **CI Status**: All checks passing on master branch

### Step-by-Step Release

#### 1. Preparation

```bash
# Ensure you're on master with latest changes
git checkout master
git pull origin master

# Verify clean working directory
git status

# Run tests to ensure everything works
cargo test --lib
```

#### 2. Version Bump and Tagging

```bash
# For patch releases (bug fixes, minor improvements)
cargo release patch

# For minor releases (new features, backward compatible)
cargo release minor

# For major releases (breaking changes)
cargo release major
```

This command will:
- Run pre-release tests automatically
- Update version in `Cargo.toml` and `Cargo.lock`
- Create a git commit with the new version
- Create a git tag (e.g., `v0.1.6`)
- **Not push** (controlled by `release.toml` configuration)

#### 3. Trigger Automated Release

```bash
# Push the commit and tag to trigger GitHub Actions
git push origin master --tags
```

#### 4. Monitor Release Process

1. **Check GitHub Actions**: Visit the [Actions tab](https://github.com/cinnes/ynab-mcp/actions) to monitor progress
2. **Verify Release Jobs**:
   - ✅ Create Release
   - ✅ Build Binaries (Linux, macOS, Windows)
   - ✅ Publish to crates.io
3. **Confirm Artifacts**: Ensure all binaries are attached to the GitHub release

### Configuration

The release process is configured via `release.toml`:

```toml
# Don't push tags (manual control)
push = false
# Don't publish to crates.io (GitHub Actions handles this)
publish = false
# Run tests before release
pre-release-hook = ["cargo", "test", "--lib"]
# Single commit for version bump
consolidate-commits = true
# Custom commit message
pre-release-commit-message = "chore: release version {{{version}}}"
# Tag message format
tag-message = "v{{{version}}}"
```

## 🔧 GitHub Actions Workflow

The automated release workflow (`.github/workflows/release.yml`) includes:

### Build Matrix
- **Linux**: `x86_64-unknown-linux-gnu`
- **macOS**: `x86_64-apple-darwin`, `aarch64-apple-darwin`
- **Windows**: `x86_64-pc-windows-msvc`

### Release Steps
1. **Create Release**: Generate GitHub release with automated changelog
2. **Build Binaries**: Compile optimized binaries for all platforms
3. **Upload Assets**: Attach binaries to GitHub release
4. **Publish Crate**: Deploy to crates.io for `cargo install`

### Quality Gates
- ✅ Version validation (Cargo.toml matches git tag)
- ✅ Test suite execution
- ✅ Binary verification and permissions

## 📦 Distribution Channels

Released artifacts are distributed through multiple channels:

### GitHub Releases
- **Binary downloads**: Direct platform-specific executables
- **Source archives**: Automatically generated by GitHub
- **Release notes**: Auto-generated changelog from commits

### Crates.io
- **Cargo installation**: `cargo install ynab-mcp --version X.Y.Z`
- **Dependency usage**: Available for other Rust projects
- **Version history**: Complete release timeline

### Docker Hub (Future)
- **Container images**: `docker pull ynab-mcp:X.Y.Z`
- **Platform variants**: Multi-architecture support
- **Tagged releases**: Immutable version references

## 🐛 Troubleshooting

### Common Issues

#### Release Fails - Cargo.lock Mismatch
```bash
# Fix: Update and commit Cargo.lock
cargo update --package ynab-mcp
git add Cargo.lock
git commit -m "chore: update Cargo.lock"
```

#### GitHub Actions Fails - Version Conflict
```bash
# Check if version already exists on crates.io
cargo search ynab-mcp

# If needed, bump to next version
cargo release patch
```

#### Tests Fail During Release
```bash
# Run tests locally with same environment
YNAB_API_TOKEN="test-token" YNAB_BLOCK_TEST_TOKENS="false" READ_ONLY_MODE="true" cargo test --lib

# Fix any failing tests before re-attempting release
```

### Emergency Fixes

For critical patches that need immediate release:

```bash
# Create hotfix branch from tag
git checkout v0.1.5
git checkout -b hotfix/critical-fix

# Make minimal changes and test
# ... fix implementation ...

# Release patch version
cargo release patch
git push origin hotfix/critical-fix --tags

# Merge back to master
git checkout master
git merge hotfix/critical-fix
git push origin master
```

## 📋 Release Checklist

Use this checklist for consistent releases:

### Pre-Release
- [ ] All CI checks passing on master
- [ ] No uncommitted changes
- [ ] Release notes prepared (if manual)
- [ ] Breaking changes documented
- [ ] Migration guide updated (for major releases)

### Release Execution
- [ ] `cargo release [patch|minor|major]` successful
- [ ] Git tag created correctly
- [ ] `git push origin master --tags` executed
- [ ] GitHub Actions workflow triggered

### Post-Release Verification
- [ ] GitHub release created with binaries
- [ ] Crates.io updated with new version
- [ ] All binary downloads functional
- [ ] Documentation reflects new version
- [ ] Community notifications sent (if applicable)

## 🔄 Version Strategy

### Semantic Versioning

We follow [SemVer](https://semver.org/) strictly:

- **MAJOR** (X.0.0): Incompatible API changes, breaking changes
- **MINOR** (0.X.0): New functionality, backward compatible
- **PATCH** (0.0.X): Bug fixes, backward compatible

### Release Cadence

- **Patch releases**: As needed for bug fixes and minor improvements
- **Minor releases**: Monthly or when significant features are ready
- **Major releases**: Planned for significant architectural changes

### Pre-release Versions

For testing major changes:

```bash
# Create pre-release version
cargo release --pre-release alpha minor
# Results in: 0.2.0-alpha.1

# Subsequent alpha releases
cargo release --pre-release alpha patch
# Results in: 0.2.0-alpha.2
```
